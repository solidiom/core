# Contributing to Solidiom

Thank you for your interest in contributing to Solidiom. This document covers
the process, requirements, and expectations for all contributions.

## Code of Conduct

Be respectful, constructive, and professional. Harassment, discrimination, and
disruptive behavior are not tolerated.

## How to Contribute

### Reporting bugs

Open a GitHub Issue with:

- A clear title and description.
- Steps to reproduce.
- Expected vs. actual behavior.
- Environment details (OS, browser, Node version).

For **security vulnerabilities**, use [GitHub private vulnerability reporting](https://github.com/openCenter-cloud/solidiom/security/advisories/new) instead. See `SECURITY.md`.

### Suggesting features

Open a GitHub Discussion in the "Ideas" category. Include the use case,
proposed behavior, and any alternatives considered.

### Submitting code

1. Fork the repository and create a feature branch from `main`.
2. Make your changes following the project conventions (see below).
3. Ensure all checks pass locally:
   ```sh
   pnpm install
   pnpm typecheck
   pnpm build
   pnpm test
   pnpm format:check
   ```
4. Open a pull request with a clear description.

## Developer Certificate of Origin (DCO)

All contributions must include a DCO signoff. This certifies that you wrote
the contribution or have the right to submit it under the project's licenses.

### What is DCO?

The [Developer Certificate of Origin](https://developercertificate.org/) is a
lightweight mechanism for contributors to certify that they have the right to
submit their contribution under the project's open-source license.

### How to signoff

Add a `Signed-off-by` line to every commit message:

```
Signed-off-by: Your Name <your.email@example.com>
```

Use `git commit -s` to add this automatically.

### Multiple authors

If a commit has multiple authors, each must add their own signoff line.

### What if I forgot?

Amend your commits to add the signoff before the PR is merged:

```sh
git commit --amend -s
git push --force-with-lease
```

## Contribution Requirements

### Pull request checklist

Every PR must:

- [ ] Include DCO signoff on all commits.
- [ ] Pass typecheck, build, and tests.
- [ ] Follow the project's formatting (Prettier).
- [ ] Include relevant tests for new behavior.
- [ ] Include accessibility validation when UI changes.
- [ ] Update English and Spanish content when user-facing text changes.
- [ ] Not introduce new diagnostics or type errors.
- [ ] Not bypass pre-commit hooks (`--no-verify` is not allowed).

### Provenance requirements

- Contributions must be original work or properly attributed.
- Do not submit code generated by tools trained on non-permissive codebases
  without verifying the output is independently licensable.
- AI-assisted contributions are acceptable if the contributor verifies
  correctness, tests, and licensing compatibility.

### Code style

- TypeScript strict mode.
- Prettier formatting (run `pnpm format` before committing).
- Explicit return types on public functions.
- JSDoc comments on exported APIs.
- No `any` types without documented justification.

### Commit messages

Use conventional commit format:

```
type(scope): short description

Longer description if needed.

Signed-off-by: Your Name <your.email@example.com>
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`.

## AI-Assisted Contributions

AI-assisted and AI-generated contributions are welcome in this project.

We consider AI tools—including coding assistants, large language models, and
autonomous or semi-autonomous development agents—to be development tools. Code,
documentation, tests, designs, issues, pull requests, and other content produced
wholly or partially with AI assistance will be evaluated on the **same technical
merits and community standards as any other contribution**.

The use of AI neither disqualifies a contribution nor lowers the standards
required for acceptance.

Contributors remain responsible for everything they submit. In particular,
contributors are expected to:

- **Understand and stand behind their contribution.** Contributors should be
  able to explain, review, modify, and maintain the work they submit.
- **Verify correctness and quality.** AI-generated output must receive
  appropriate human review, testing, and validation before submission.
- **Comply with project licensing requirements.** The terms of any AI tool used
  must not impose restrictions that conflict with this project's license or
  contribution policies.
- **Respect copyright and intellectual property.** Contributors must ensure that
  generated content does not improperly incorporate third-party copyrighted
  material.
- **Provide required attribution and provenance.** Third-party code, content, or
  other material must retain any attribution, notices, or licensing information
  required by its license.
- **Meet security and maintainability standards.** AI assistance does not exempt
  a contribution from security review, testing, documentation, architectural
  requirements, CI checks, or normal code review.
- **Avoid shifting the review burden to maintainers.** Large volumes of
  unreviewed, low-quality, unexplained, or mechanically generated contributions
  may be rejected regardless of whether AI was involved.

The core principle is:

> **AI assistance is welcome; contributor responsibility remains with the human
> submitting the contribution.**

AI should be used to augment engineering judgment, not replace it. Maintainers
may request additional explanation, testing, provenance information, or
disclosure of significant AI assistance when reasonably necessary to evaluate a
contribution.

This policy is intentionally aligned with the broader open-source approach
advocated by the Linux Foundation and reflected in CNCF community guidance:
AI-generated contributions can participate in normal open-source development,
provided they meet the same expectations for quality, security, licensing,
provenance, accountability, and human review.

### Related guidance

- **Linux Foundation — Guidance Regarding Use of Generative AI Tools for Open
  Source Software Development:**
  <https://www.linuxfoundation.org/legal/generative-ai>
- **CNCF — Sustaining Open Source in the Age of Generative AI:**
  <https://www.cncf.io/blog/2026/03/10/sustaining-open-source-in-the-age-of-generative-ai/>
- **CNCF — The State of AI in CNCF Projects:**
  <https://www.cncf.io/blog/2026/04/29/the-state-of-ai-in-cncf-projects-a-first-look-at-the-data/>

Individual projects and organizations may establish additional requirements for
AI-assisted contributions where appropriate.

  these terms.

## Review Process

1. A maintainer will review your PR within a reasonable timeframe.
2. Reviews focus on correctness, accessibility, performance, and consistency.
3. Requested changes must be addressed before merge.
4. Maintainers may edit or squash commits during merge.

## What We Don't Accept

- PRs without DCO signoff.
- Breaking changes without prior discussion.
- Features that duplicate existing primitives or bypass architectural decisions.
- Content that violates licensing boundaries.
- Automated bulk PRs without prior maintainer approval.
