> **Purpose:** For Solidiom contributors, shows how to author a canonical recipe definition and generate its output for `recipes-css`, `recipes-tailwind`, and `recipes-unocss`.

**Revised:** 2026-07-30
**Contract reference:** `docs/contracts/recipe-contract.md`
**Breakdown:** (delivered; task breakdown archived — see git history for `docs/recipe-001-canonical-recipe-contract.md`)
**Status:** current. The canonical contract, its vocabulary, its token identities, its validator, and all three emitters (RECIPE-001/002/003/004) have shipped and are enforced in CI. The cross-profile parity audits and computed-style harness (RECIPE-005) and the src/source parity checks (RECIPE-006) have also shipped. Every recipe in `recipes-css`, `recipes-tailwind`, and `recipes-unocss` is generated from `tools/recipe-contract-definitions.ts`. You edit a definition and re-run the corresponding emitter; you do not hand-write a stylesheet or a `cva()` call in a recipe package.

---

## 1. What changed, and what that means for you today

RECIPE-001 defined one canonical recipe definition — slots, variants, states, compound variants, tokens, exceptions — from which all three profiles are generated. RECIPE-002/003/004 built the emitters that do the generating. The rules in §3 describe what those emitters produce and what the validator rejects; they are not migration guidance, they are how the system works today.

| Concern           | Before RECIPE-002/003/004          | Now                                                                                      |
| ----------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| Source of truth   | Hand-written CSS + TSX per profile | One definition per recipe in `tools/recipe-contract-definitions.ts`                      |
| Profiles in scope | `recipes-css`, `recipes-tailwind`  | `recipes-css`, `recipes-tailwind`, `recipes-unocss` — all generated                      |
| Variants          | Hand-written `cva()` class strings | Generated into a `<name>.variants.ts` module per profile                                 |
| Tokens            | Profile-local names                | Canonical semantic token set (`css`/`tailwind`/`unocss`/`site`), profile-local mechanism |
| Parity            | File pairing only                  | File pairing, plus generation from one shared source                                     |

### Superseded guidance

A previous revision of this guide instructed authors to let profiles diverge in token strategy and not to introduce cross-profile contracts. **That guidance is withdrawn.** The canonical contract _is_ the cross-profile contract: `tools/recipe-contract-tokens.ts` defines 60 token identities with their per-namespace spellings, and the validator rejects a reference to anything else. See §3.5 for the replacement rule and `docs/contracts/recipe-contract.md` §4 for the model.

## 2. The architecture you are authoring into

### 2.1 Each profile ships two generated emission forms

Every recipe's stylesheet form exists inside its profile, generated from the same definition. The class-string form (`.variants.ts`) is generated **only for a scope that declares a `variants` axis** — currently badge and button; a scope with no variants axis has a stylesheet form only, and that is correct, not a gap. The emitters keep both forms in agreement by construction where both exist:

| Form         | File                             | Consumed as                                                                    | Generated by                                          |
| ------------ | -------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------- |
| Stylesheet   | `src/styles/<name>.css`          | An imported CSS subpath; selector-based                                        | `tools/recipe-emit-{css,tailwind,unocss}.ts`          |
| Class string | `src/recipes/<name>.variants.ts` | Imported by the hand-written `src/recipes/<name>.tsx` wrapper as `class={...}` | Same emitter, only for a scope with a `variants` axis |

`tools/audit-recipe-dual-emission.ts` still checks the pairing; it now also derives composition exceptions from a definition's `ownership` field (§3.7) rather than a hand-maintained allowlist. `tools/audit-recipe-parity.ts` (RECIPE-005) checks the stronger, definition-driven version of the same thing: every slot and state a definition declares actually appears in each profile's stylesheet (not merely that whatever the stylesheet contains is rendered by the wrapper), that a `.variants.ts` module exists exactly when a scope declares a `variants` axis, and that all three profiles cover the same scopes/slots/states as each other. The `.tsx` wrapper component itself (`src/recipes/<name>.tsx`) stays hand-written in every profile — it composes the primitive and, for a scope with variants, imports the generated `.variants.ts` module. The dual-emission audit reads this file to find the primitive import and the rendered parts, which is why a generator-owned `.tsx` would break it.

### 2.2 Profile status

| Package                      | Recipes | Stylesheets                               | Notes                                                                                                                  |
| ---------------------------- | ------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `@solidiom/recipes-css`      | 32      | 32 + `index`, `prose`, `typeset`          | Generated (RECIPE-002). Tokens via `var(--ui-*, fallback)`                                                             |
| `@solidiom/recipes-tailwind` | 32      | 32 + `index`, `theme`, `prose`, `typeset` | Generated (RECIPE-003). `@apply` inside `@layer components`; `theme.css` hand-maintained until THEME-003               |
| `@solidiom/recipes-unocss`   | 32      | 32 + `index`                              | Generated (RECIPE-004). Plain declarations via the `unocss` token namespace — same `--ui-*` custom properties as `css` |

The 32 covered primitives: accordion, alert, avatar, badge, breadcrumb, button, card, checkbox, combobox, command-palette, data-table, dialog, field, input, kbd, menu, meter, navigation-menu, pagination, popover, progress, radio-group, resizable-panels, scroll-area, select, sheet, spinner, switch, tabs, toast, toolbar, tooltip.

Know which of these blocks a pull request, because they are not equivalent:

| Cross-profile coverage/state/exception parity     | `pnpm run audit:recipe-parity`                                        | **Yes** — same gate section (RECIPE-005)                                               |
| Computed-style parity                             | `pnpm run test:recipe-parity`                                         | **Yes** — `ci-packages.yml` `test-browser` job (RECIPE-005 phase 3)                    |
| Recipe-contract selectors                         | `pnpm run audit:recipe-contract`                                      | **Yes** — same gate section                                                            |
| Generated output is current                       | `pnpm run recipe:emit:{css,tailwind,unocss}:check`                    | **Yes** — same gate section, one check per profile                                     |
| Typecheck                                         | `pnpm typecheck`                                                      | Yes                                                                                    |
| Build                                             | `pnpm build`                                                          | Yes                                                                                    |

| `src`/`source` parity and export-map completeness | `pnpm run audit:package-source-parity`, `tests/package-source-parity` | **Yes** — recipe packages included since RECIPE-006; CLI parity included since CLI-001 |

#### What the selector audit actually rejects

`tools/audit-recipe-contract.ts` reads only `.css` files. It permits attribute selectors, state pseudo-classes, structural pseudos, pseudo-elements, and element descendant selectors, and rejects:

- a class selector with no `[data-` qualifier on the same line;
- an ID selector;
- a `data-*` attribute outside the semantic vocabulary exported by `@solidiom/runtime`.

A data-qualified class selector (`[data-part="root"].solidiom-btn--destructive`) passes — that is the shape the emitters use to back a variant class with real declarations (§3.1). The selector audit is the floor; `pnpm run recipe:contract` (§4.5) is the real check.

## 3. The rules the emitters enforce

These are enforced by `tools/recipe-contract-validate.ts` and reflected in every generated file. If you edit a definition and violate one of these, `pnpm run recipe:contract` fails before the emitters ever run.

### 3.1 Every class a definition backs must resolve to real declarations

A variant or compound-variant axis produces a class name (`<prefix>--<value>` or `<prefix>--<value1>-<value2>`), and the emitter always writes the matching selector into the same profile's stylesheet. There is no way to add a variant value with no backing declarations — `tools/recipe-contract-validate.ts` §3.1 rejects an empty declaration group before an emitter runs.

This rule exists because it was broken before RECIPE-002: `recipes-css/src/recipes/button.tsx` used to emit `solidiom-btn` plus eleven `solidiom-btn--*` variant classes with no definitions anywhere in `packages/recipes-css`. Do not hand-add a class to a wrapper's `class={...}` that the generated `.variants.ts` module does not produce.

### 3.2 State goes on the part that renders it — never on an ancestor

If root state changes how a child part looks, the child part must carry its own `data-state` in the definition, and the emitters style it directly:

```ts
// tools/recipe-contract-definitions.ts — switch, correct shape
{
  part: "thumb",
  states: {
    on: { transform: "translateX(1.25rem)" },
    off: { transform: "translateX(0)" },
  },
}
```

Before RECIPE-002 both profiles' `switch.css` styled the thumb through an ancestor selector on the root's state — valid CSS, but unexpressible in the class-string form (Tailwind would need `group` plus `group-data-[state=on]:`, and UnoCSS's `presetSolidiom` variants append their selector to the same element only). The generated stylesheets no longer contain that pattern for any of the 32 scopes. If a definition needs a child to react to a parent's state, the primitive must emit `data-state` on the child — fix the primitive, do not add an ancestor selector to the definition.

### 3.3 The two forms match in coverage because they share a source

For every recipe, the same set of slots, variants, and states is reachable from both the stylesheet and the class-string module, because both are generated from `resolveRules()` walking the same definition in `tools/recipe-emit-core.ts`. There is no separate coverage step to remember — the shared cascade resolution is what makes divergence structurally impossible rather than merely checked for.

### 3.4 Overlay recipes must style their presence states

Any recipe for a primitive that retains its DOM through `createPresence` while closing — currently Alert Dialog, Command Palette, Date Picker, Dialog, Drawer, Navigation Menu, Popover, Sheet, and Tooltip — must style `data-state="open"` and `data-state="closed"` on the parts that appear and disappear, in the definition. `tools/recipe-contract-validate.ts` §3.4 rejects a presence-scope definition where no slot styles `open`/`closed`. `SCOPE_STATES` alone is not enough to identify this set: Accordion, Menu, and Select also emit open/closed state, but unmount their content immediately, while Toast has no open/closed state — presence styling would be meaningless for those primitives.

### 3.5 Token identity is shared; token mechanism is profile-local

This replaces the withdrawn "let profiles diverge" guidance.

- **Shared:** the semantic token _identity_ — what `primary`, `primary-foreground`, `surface-muted`, `border`, `radius` mean. The canonical set is `tools/recipe-contract-tokens.ts`; `pnpm run recipe:contract` rejects any reference outside it.
- **Profile-local:** how that identity is emitted. `css` and `unocss` spell it `var(--ui-<token>, <fallback>)`, sharing the same runtime namespace; `tailwind` spells it as a theme utility (`bg-primary`, `text-muted-foreground`), registered by `packages/recipes-tailwind/src/styles/theme.css` and resolved from the same `--ui-*` namespace.

Setting `--ui-primary` once now themes the `css` and `unocss` profiles simultaneously, and the same value flows into `tailwind`'s theme registration. A token identity a namespace cannot express is listed as `null` in its `namespaces` map, and `pnpm run recipe:contract` prints those gaps per definition. As of RECIPE-002/003/004, no definition has an unclosed `css`, `tailwind`, or `unocss` gap — only `site` (BRAND-002/THEME-002's namespace) has remaining gaps. If a recipe needs an identity the canonical set lacks, add it under a THEME-001 decision rather than locally in one profile.

### 3.6 The attribute vocabulary is closed

Use only attributes in the semantic vocabulary, exported from `@solidiom/runtime` and defined in `packages/runtime/src/dom/semantic-vocabulary.ts`:

| Attribute          | Values                                                                                                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-scope`       | The primitive package name                                                                                                                                                       |
| `data-part`        | The part name                                                                                                                                                                    |
| `data-state`       | Per-scope state value (`open`, `closed`, `checked`, `unchecked`, `on`, `off`, `active`, `indeterminate`)                                                                         |
| `data-orientation` | `horizontal`, `vertical`                                                                                                                                                         |
| Boolean flags      | `data-disabled`, `data-loading`, `data-readonly`, `data-required`, `data-invalid`, `data-placeholder`, `data-highlighted`, `data-selected` — present or absent, never `="false"` |

Two attributes sit outside the helper and are set directly by primitives: `data-side` (sheet, drawer, positioned overlays) and `data-size` (composite recipes, see §5). Both are legal in recipe CSS.

`data-scope` must equal the primitive package a definition's `scope` field names. `tools/recipe-contract-validate.ts` §3.6 rejects a scope not in `SCOPE_STATES`, and the dual-emission audit checks the same equality against the hand-written wrapper's import.

### 3.7 Composition exceptions are `ownership` on the slot, with a mandatory reason

When a definition styles a part the TSX wrapper does not render — repeatable items, optional titles, consumer-supplied collection content — declare `ownership: "consumer"` on that slot with an `ownershipReason`. `tools/recipe-contract-validate.ts` §3.7 rejects a non-`"recipe"` slot with no reason.

This replaced `COMPOSED_PART_ALLOWLIST` in `tools/audit-recipe-dual-emission.ts` for every scope with a canonical definition — the audit now checks `ownership` first and falls back to the (now-empty, for all 32 shipped scopes) allowlist only for a scope with no definition. Migrating the allowlist surfaced a real mismatch during RECIPE-002: several slots were marked `ownership: "recipe"` in the definitions despite their wrappers never rendering them (accordion's `item`/`trigger`/`content`, alert's `title`/`description`, menu's `item`/`separator`, popover's `close`, select's `item`, tabs' `list`/`trigger`/`content`, toast's `title`/`description`/`close`/`region`) — all corrected to `ownership: "consumer"`.

Adapter-owned geometry is a separate exception: `ownership: "adapter"` plus `adapterPort` and `adapterOwnedProperties`. See `docs/contracts/recipe-contract.md` §5.

### 3.8 Solid 2 requirements for TSX wrappers

Wrappers are Solid 2 components and follow the same rules as primitives (see `docs/architecture/solid2-migration-notes.md`):

- Import `type JSX` from `@solidjs/web`, never from `solid-js` — `solid-js` has no `JSX` export in Solid 2. Nothing enforces this: `docs/architecture/solid2-migration-notes.md` claims a `no-jsx-from-solid-js` rule exists, but `packages/eslint-plugin-solidiom/src/rules/` contains no such rule. Check the import by hand.
- Accept and forward `class`, and accept `style` and `ref` where the part renders a DOM element. A wrapper that does not accept `class` forces consumers into invalid nesting.
- Use bare boolean prop names: `loading`, `disabled`, `pressed` — never `isLoading`.
- No `asChild`. Solid has no `cloneElement`. Export a variants function for composition instead.
- Do not destructure props; read `props.x` in render expressions.

## 4. Adding or changing a recipe

You edit `tools/recipe-contract-definitions.ts` and re-run the emitters. You do not hand-write a stylesheet or a `cva()` call in any recipe package.

### 4.1 Pick or find the scope name

Kebab-case, equal to the primitive package name. `REFERENCE_DEFINITIONS` in `tools/recipe-contract-definitions.ts` is keyed by scope; check what exists there before adding a new one.

### 4.2 Author or edit the definition

Add or edit a `RecipeDefinition` — slots, `base`/`states`/`flags`/`pseudos`, `variants`, `compoundVariants` — following the shape documented in `docs/contracts/recipe-contract.md` §2. Reference token identities from `tools/recipe-contract-tokens.ts` for anything a token covers (§3.5); use literals only for lengths, keywords, and timing. Declare `ownership` and a reason for anything the wrapper does not render (§3.7). Put state on the slot that carries it (§3.2).

### 4.3 Validate the definition before emitting

```sh
pnpm run recipe:contract
```

Fix every violation the validator reports before running an emitter — the emitters trust the definitions are valid and do not re-check contract rules themselves.

### 4.4 Run the emitters

```sh
pnpm run recipe:emit:css
pnpm run recipe:emit:tailwind
pnpm run recipe:emit:unocss
```

Each writes `src/styles/<name>.css` for every scope, `src/recipes/<name>.variants.ts` for a scope with a `variants` axis, and regenerates `src/styles/index.css`. The UnoCSS emitter additionally regenerates `packages/unocss-preset/src/generated-variant-rules.ts`, the static UnoCSS rules the preset uses to resolve a variant class without a stylesheet import. Every emitter is idempotent and formats its own output through the repo's Prettier config — running it twice with no definition change produces no diff.

If you added a new scope, also hand-write `src/recipes/<name>.tsx` in each profile (§2.1) — the wrapper component that composes the primitive and, for a scope with variants, imports the generated `.variants.ts` module. Follow the shape of an existing wrapper in the same profile and §3.8's Solid 2 rules. Then wire it into that profile's `src/index.ts` (re-export the wrapper) and `src/meta.ts` (add to `supportedPrimitives`).

### 4.5 Verify

```sh
# Canonical contract — CI-enforced
pnpm run recipe:contract

# Generated output matches the definitions — CI-enforced, one per profile
pnpm run recipe:emit:css:check
pnpm run recipe:emit:tailwind:check
pnpm run recipe:emit:unocss:check

# Drift check — CI-enforced
pnpm run audit:recipe-drift

# Cross-profile coverage/state/exception parity — CI-enforced (RECIPE-005)
pnpm run audit:recipe-parity

# Computed-style parity across profiles — CI-enforced (RECIPE-005 phase 3)
pnpm run test:recipe-parity

# Selector audit — CI-enforced
pnpm run audit:recipe-contract   # must print 0 violations

# Contract, vocabulary, token, and emitter fixtures
pnpm exec vitest run tools/recipe-contract-validate.test.ts tools/recipe-contract-vocabulary.test.ts tools/recipe-contract-tokens.test.ts tools/recipe-contract-definitions.test.ts tools/audit-recipe-contract.test.ts tools/recipe-emit-core.test.ts tools/recipe-emit-css.test.ts tools/recipe-emit-tailwind-utilities.test.ts tools/recipe-emit-tailwind.test.ts tools/recipe-emit-unocss.test.ts

# Build and typecheck all three profiles
pnpm --filter @solidiom/recipes-css --filter @solidiom/recipes-tailwind --filter @solidiom/recipes-unocss build
pnpm --filter @solidiom/recipes-css --filter @solidiom/recipes-tailwind --filter @solidiom/recipes-unocss typecheck
```

If you touched `packages/runtime/src`, rebuild it before running the tools tests — they resolve `@solidiom/runtime` through `dist/`:

```sh
pnpm --filter @solidiom/runtime build
```

The full acceptance gate, including all of the above plus every primitive build and the axe accessibility scans:

```sh
pnpm run gate:full
```

## 5. Composite recipes

When a recipe styles a **subtree of arbitrary HTML** — rendered Markdown, rich text — use element descendant selectors under an attribute-scoped root. `prose` and `typeset` are composite scopes with no primitive behind them; they are excluded from the emitters' generation (`UTILITY_STYLESHEETS`/`NON_GENERATED_STYLESHEETS` in the emitter source) and stay hand-written:

```css
[data-scope="prose"] h1 {
  /* ... */
}
[data-scope="prose"] p {
  /* ... */
}
[data-scope="prose"] a {
  /* ... */
}
```

Differences from a granular recipe:

- no `data-part` on children — consumers do not control the inner HTML structure;
- size and density variants go on the root: `[data-scope="prose"][data-size="lg"]`;
- element descendant selectors are legal here — §3.2 forbids _ancestor-state_ selectors reaching a named part, not element styling inside a composite subtree;
- no canonical definition needed — a composite scope has no primitive to model in `tools/recipe-contract-definitions.ts`.

We use `[data-scope="prose"]` rather than the industry-conventional `.prose` because it stays inside the attribute contract, needs no plugin dependency, and matches every other recipe.

## 6. Troubleshooting

| Symptom                                                                                     | Cause                                                                                             | Fix                                                                                                                               |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `recipe:emit:*:check` fails in CI                                                           | A definition changed but the emitter was not re-run                                               | Run `pnpm run recipe:emit:{css,tailwind,unocss}` and commit the result                                                            |
| Selector audit: "Class selector without data-\* qualifier"                                  | An emitter bug, or a hand-edited generated file                                                   | Never hand-edit a file with a `GENERATED by tools/recipe-emit-*.ts` header — edit the definition and re-run the emitter           |
| Drift check: "CSS file has no matching TSX recipe"                                          | Added a stylesheet without its `.tsx` wrapper                                                     | Add `src/recipes/<name>.tsx` (§4.4), or name the file as a utility stylesheet                                                     |
| Drift check: "data-part is not rendered by ... and has no documented composition exception" | Definition styles a part the wrapper does not render, and the slot has no `ownership: "consumer"` | Render it, or set `ownership: "consumer"` with `ownershipReason` (§3.7) — then re-run `pnpm run recipe:contract` and the emitters |
| Drift check: "data-scope does not match imported primitive"                                 | The definition's `scope` differs from the wrapper's imported package                              | Fix whichever one is wrong                                                                                                        |
| `pnpm run recipe:contract` reports "cannot express" for `css`/`tailwind`/`unocss`           | A token reference has no spelling in that namespace                                               | Add the spelling in `tools/recipe-contract-tokens.ts` under a THEME-001 decision — do not invent a profile-local workaround       |
| `dist/styles/<name>.css` missing after build                                                | `index.css` not regenerated, or the profile's build not re-run                                    | Re-run the emitter, then `pnpm --filter <profile-package> build`                                                                  |
| Consumer: "Package subpath not defined"                                                     | Missing `exports` entry for a new scope                                                           | Add `"./styles/<name>.css": "./dist/styles/<name>.css"` to the profile's `package.json`                                           |
| TypeScript cannot find the exported symbol                                                  | Missing re-export in `src/index.ts`                                                               | Add it (§4.4)                                                                                                                     |
| Variant has no visual effect                                                                | Definition change not yet emitted                                                                 | Re-run the emitter for that profile                                                                                               |
| Child part ignores root state                                                               | Ancestor-state pattern reintroduced, or the primitive does not emit `data-state` on the child     | §3.2 — put the state on the slot in the definition and confirm the primitive emits it                                             |
