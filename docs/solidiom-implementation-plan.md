> **Purpose:** For Solidiom project leads and contributors, tracks the phased implementation of Solidiom v0.6 → beta release → Solid 2 GA and stable v1.0 → strict v2.0 against the design in `opencenter-solidiom.md`, records the tooling and process decisions made during plan creation, and provides a checklist for progress.

## Overview

This document pairs with `opencenter-solidiom.md` v0.6. The design doc is the **what and why**; this document is the **how, when, and by whom**. Every task maps to a §21 phase or an explicitly plan-introduced tooling workstream and cites the design-doc sections it satisfies. Check tasks off as they complete.

Progress convention: `[ ]` open, `[~]` in progress, `[x]` complete, `[!]` blocked (add reason).

## Locked decisions

The core architectural decisions made during plan creation and subsequent roadmap reviews are summarized below. Full original rationale is in §27 of `opencenter-solidiom.md`.

| #   | Area            | Choice                                                                                                                |
| --- | --------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1   | Scope           | Phases 0–3 through initial beta; Phase 3A for compile-time beta incubation; independent Phase 3B authoring tooling; Phase 4 for Solid 2 GA/stable v1.0; Phase 5 for strict v2.0 |
| 2   | Monorepo        | Nx (integrated) + pnpm workspaces + Changesets                                                                        |
| 3   | Build tools     | `tsup` for pure-TS; Vite lib mode + `vite-plugin-solid` for JSX. Dual-emit `dist/` compiled + `source/` canonical TSX |
| 4   | Testing         | Vitest with `@vitest/browser` (Playwright provider); `expect-type` for type tests                                     |
| 5   | CLI             | Public CLI: `clipanion` + `@clack/prompts` + `picocolors` + `zod`; contributor scaffolding remains workspace-internal |
| 6   | Registry        | npm-hosted tarballs + signed immutable catalogs in Cloudflare R2, with signed mutable `next`/`beta`/`latest` channel pointers |
| 7   | AST toolchain   | `ts-morph` + TSESTree + `oxc-parser`, ast-grep authoring layer for pattern migrations                                 |
| 8   | Three-way merge | `node-diff3` + ts-morph AST validation + postcss for CSS; patch fallback on validation failure                        |
| 9   | Signatures      | `@sigstore/verify` in CLI; `@sigstore/sign` in `@solidiom/release-tools` (CI only); Node `crypto` for Mode B          |
| 10  | Solid 2 matrix  | 3-beta rolling window; matrix `{low, mid, high} × {node 20, node 22} × chromium`                                      |
| 11  | Recipes         | Both stylesheet + component-shaped TSX from canonical source; CSS + Tailwind Phase 1, UnoCSS Phase 2                  |
| 12  | Test doubles    | Deterministic doubles for every capability + second production positioning adapter                                    |
| 13  | Docs            | SolidStart + `@mdx-js/solid` + custom Diátaxis-aware sidebar/routing                                                  |
| 14  | Benchmarks      | Playwright + `mitata` + `size-limit` under `@solidiom/bench`                                                         |

Policy defaults (pushback-able): MIT license · GitHub Actions CI · Changesets-per-PR (`next` for continuous prereleases, `beta` only after the Phase 3 release gate, `latest` for stable tags) · CycloneDX 1.5 JSON SBOM · legacy sunset default deprecated 2 minors + removed next major · playground routes embedded in `apps/docs`.

### Phase 3B — Generative authoring tooling (unversioned, independent)

Phase 3B is an independent post-beta contributor-tooling milestone. It may run alongside Phase 4 and does not gate v1.0 or v2.0 unless explicitly added to a future release criterion. It changes no runtime behavior or public primitive API. Today, adding a primitive requires hand-editing roughly 15 files across multiple packages (`docs/adding-a-primitive.md`), while `tools/primitive-completion-gate.ts` only validates those edits afterward. Phase 3B replaces that workflow with package-local manifests, an internal workspace generator, deterministic synchronization, and CI drift enforcement.

**Authority model.** `tools/primitive-contract.ts` owns the versioned Zod manifest schema and typed conditional generation rules. Every scaffold-managed primitive package owns a `packages/<name>/primitive.json` manifest with `visibility: public|internal|experimental`; package manifests may declare multiple public `components[]`, as the Calendar manifest will for Calendar and RangeCalendar. Manifests contain per-package facts; authored source, behavioral tests, and demo implementations contain behavior; generated indexes and wiring are downstream artifacts. `registry/index.json` is output, never generator input. `tools/primitive-completion-policy.json` is removed, and its classifications move into manifests. Existing manifests are bootstrapped from packages/registry, reviewed by humans, and landed atomically before consumers switch.

**Ownership model.** Fully generated mechanical files (umbrella and recipe barrels, registry indexes, generated registration) carry a do-not-edit header and are deterministically rewritten. Mixed JSON files are parsed and merged only at generator-owned keys, preserving unrelated metadata. Behavior source, comprehensive tests, and demo implementations are scaffolded once and never overwritten. `scaffold sync` may create newly required missing starter files after a manifest adds a component, but it never modifies an existing scaffold-once file. Constrained, schema-validated manifest overrides may add or exclude dependencies, files, capabilities, or integrations and must include a reason; arbitrary generator hooks are forbidden.

**Safety and validation.** Commands are workspace-internal (`pnpm scaffold primitive`, `pnpm scaffold:sync`), not public `@solidiom/cli` API. Mutations are planned, staged, and validated before atomic application; collisions fail by default, and `--dry-run`/`--check` never mutate. Validation is layered as `primitive:package-audit`, `primitive:recipe-audit`, and `primitive:completion-gate`. The gate and generator share the contract but are also checked by independent golden positive/negative fixtures, real builds, docs/registry validation, and a temporary fixture-workspace round trip so shared defects cannot self-validate.

## Operational notes and remaining decisions

- **Registry hosting and promotion.** Production catalogs use Cloudflare R2 + Workers. Immutable `/catalogs/<version>/index.json` objects and mutable `/channels/{next,beta,latest}.json` pointers are all signed. `next` is continuous; `beta` and `latest` require their respective release gates. Workers provide caching, controlled promotion, and rollback to an earlier immutable catalog.
- **Local package publishing.** Use `pnpm pack` with isolated scratch consumers for routine package-content and install verification. Verdaccio remains the reference internal-mirror/offline-install environment for Task 57 rather than a prerequisite for every local test.
- **Solid 2 GA timing.** Phase 3 ships under Solid 2 beta. Phase 3A must complete before the first RC. Phase 4 begins only after a Solid 2 GA release is available.
- **AT verification vendor.** Select the external audit vendor for Task 71. Initial beta requires automated axe/keyboard results and VoiceOver records across the entire public surface; NVDA, JAWS, and TalkBack are explicit Phase 4 requirements.
- **Docs versioning.** Confirm SolidStart route grouping per version in Phase 4 before the first stable docs branch.
- **Active ownership.** No repository `CODEOWNERS` file exists. The active execution matrix uses inferred functional teams and `TBD` DRIs until maintainers assign named owners; every completion claim should link durable evidence.
- **v0.6 → v0.7 boundary.** Tasks 28 and 41 promote the ESLint plugin from skeleton to shipped rules. This remains the §17.4 v0.7.x–v0.8.x transition.
- **Phase 3A ordering.** Compile-time beta features do not block the initial beta but must ship in a later beta, complete `phase3a:gate`, and become stable before the first v1.0 RC.
- **Phase 3B ownership.** Purely mechanical artifacts are fully generated, mixed JSON is merged at owned keys, and behavior/tests/demo implementations are scaffold-once. Package-local `primitive.json` manifests are authoritative; generated registry indexes and aggregators are downstream only.
- **Phase 3B release relationship.** Phase 3B is an unversioned internal milestone. It may run in parallel with Phase 4 and does not gate v1.0 or v2.0 unless a future roadmap revision explicitly changes that policy.
- **Phase 5 timing.** v2.0 is a separate breaking-release program driven by completed sunset criteria and strict defaults, not merely the availability of Solid 2 GA.
